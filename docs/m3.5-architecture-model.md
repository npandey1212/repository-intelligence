# M3.5 — ArchitectureModel Construction (`architecture_construction_rules.v1`)

## What this milestone is

```text
EngineeringModel
      ↓
architecture_construction_rules.v1     (one deterministic rule)
      ↓
ArchitectureModel  (architecture section + mappings on repository_knowledge_model.v1)
```

Input is the **existing M3 EngineeringModel** only. No re-parse of the
repository, no Tree-sitter, no second fact model, no LLM.

Canonical output:

```text
artifacts/main_2026-09-22_ef11dac/architecture/architecture_model.json
artifacts/main_2026-09-22_ef11dac/architecture/architecture_construction_rules.v1.json
```

Rulebook schema:

```text
schemas/architecture_construction_rules.v1.json
```

CLI:

```bash
python -m repo_intelligence architecture
```

## The only transformations

```text
Engineering node
  kind    = artifact
  subkind = agent_definition
        │
        │ CONTRIBUTES_TO   (mapping AR-M001)
        ▼
Architecture node
  kind    = concept
  subkind = agent           (node rule AR-N001)
```

**AR-N002 / AR-M002 — fixed orchestration boundary (evidence-backed):**

```text
onboard-workflow command
SKILLS.md
docs/workflow-diagrams.md
runbooks/data-onboarding-agent/README.md
        │  explicit engineering_node_ids only (not filename scan)
        │  CONTRIBUTES_TO  (AR-M002)
        ▼
concept:agent:data-onboarding-agent
  name = "Data Onboarding Agent"
```

**AR-R001:** elevate M3 `TRIGGERS` to architecture `TRIGGERS` only when
**both** endpoints already resolve via mappings to architecture nodes.

Nothing else becomes architecture in this milestone:

```text
agent_config    → not architecture
mcp_config      → not architecture
mcp_server_source → not architecture
Python class Agent → not architecture
external_package → not external system
IMPORTS / CONTAINS / DEPENDS_ON → not architecture relationships
arbitrary files containing "onboard" → not architecture (must be listed ids)
```

## Architecture identity

Identity describes the **architectural concept**, not the file:

```text
concept:agent:dag-agent
concept:agent:fixture-agent
```

**Not** (forbidden):

```text
concept:agent:src/foo.py
concept:agent:agent_definition:foo.md
concept:agent:AR-N001:...
```

Derivation (deterministic, no LLM):

1. `attributes.name` when present → slug
2. else filename stem of the agent definition path → slug

```text
.claude/agents/dag-agent.md  →  concept:agent:dag-agent
```

Multiple engineering nodes with the same canonical name **reuse** one
architecture node (identity collision = same concept, not a bug).

If identity cannot be established → `architecture.unresolved[]`
(`ambiguous_identity`), never a guessed id.

## Mappings

```json
{
  "id": "map:CONTRIBUTES_TO:<engineering-id>:<architecture-id>",
  "source": "artifact:agent_definition:.claude/agents/dag-agent.md",
  "target": "concept:agent:dag-agent",
  "kind": "CONTRIBUTES_TO",
  "classification": "derived",
  "evidence": [ ... ]
}
```

Every mapping has evidence copied from its engineering source node.

---

## Evidence

```text
Architecture node      → union of contributing engineering evidence (deduped)
CONTRIBUTES_TO mapping → that mapping’s engineering source evidence
```

Provenance invariant: **No evidence → no canonical architectural claim.**

Reuse the same merge/dedup/sort keys as M3 engineering — no second
provenance implementation.

---

## Architecture relationships — `TRIGGERS` only (AR-R001)

Engineering edges are **not** copied wholesale. Exactly one elevation rule:

```text
M3 engineering TRIGGERS
        │
        │ resolve source eng node → mapping → architecture node
        │ resolve target eng node → mapping → architecture node
        ▼
M4 architecture TRIGGERS   (classification = derived)
```

If either endpoint has **no architecture mapping**, the claim goes to
`architecture.unresolved[]` (`reason=missing_endpoint`) — never a guessed
`concept:workflow:…` id.

`CONTAINS` / `IMPORTS` / `DEPENDS_ON` remain engineering-only:

```text
Python A IMPORTS Python B
        ≠
Architecture A DEPENDS_ON Architecture B
```

## Why ArchitectureModel is separate

1. **Why separate from EngineeringModel** — engineering structure
   (files/modules/imports) is observed implementation; architecture is a
   derived interpretation layer. Mixing them makes it impossible to change
   interpretation without rewriting observations.
2. **Why only `agent_definition → agent`** — it is the only mapping with a
   frozen, deterministic identity and clear semantic claim in this rulebook.
3. **Why engineering relationships are not copied** — `IMPORTS` does not mean
   service dependency; automatic promotion would invent architecture.
4. **Why mappings exist** — a bridge keeps both graphs honest: engineering
   stays stable while architecture evolves under versioned rules.
5. **Why unresolved beats guesses** — parking weak claims in
   `architecture.unresolved[]` preserves auditability without polluting the
   canonical graph.

## Validation (enforced)

```text
unique architecture node ids
unique architecture relationship ids
mapping source ∈ engineering nodes
mapping target ∈ architecture nodes
relationship source ∈ architecture nodes
relationship target ∈ architecture nodes
architecture node evidence ≥ 1
mapping evidence ≥ 1
architecture relationship evidence ≥ 1
architecture relationship kind ∈ {TRIGGERS}
unresolved claims never also canonical
deterministic ids, evidence order, node order, mapping order, relationship order
engineering section unchanged and still valid
```
